Тестовое по userver
Вячеслав Савельев, БПИ264

Попробовал разобраться, на что уходит время сборки сервиса и можно ли немного её ускорить. Взял шаблон через userver-create-service --grpc --mongo --postgresql userver_study внутри Docker образа из задания. Работал на Mac с Apple M5 и 16 ГБ памяти, поэтому образ запускался через эмуляцию x86-64. Использовал Clang 18.1.8, Release сборку, Ninja и ограничения из задания: 4 ядра и 8 ГБ памяти. Остальные настройки и версии сохранил в приложенных файлах.

Для замеров подключил -ftime-trace и Clang Build Analyzer. Сравнивал обычную сборку и сборку с PCH, то есть заранее подготовленным заголовком. Для каждого варианта сначала сделал один прогревочный запуск, потом три замера. Варианты запускал по очереди, каждый раз в новом каталоге, кэши компиляции отключил. Во время команды сборки учитывал генерацию кода, компиляцию и линковку. Установка инструментов и настройка CMake в это время не входят. Собирал цель userver_study, без тестов и бенчмарков.

Из того, что получилось увидеть:
1) На разбор C++ кода суммарно ушло 25,88 с, на генерацию машинного кода 12,55 с. Несколько файлов компилируются параллельно, поэтому это не то же самое, что время ожидания всей сборки.
2) Заметную часть времени занимает сгенерированный gRPC код. Разбор четырёх файлов дал 11,07 с, ещё 4,27 с пришлось на main.cpp.
3) Общие заголовки разбираются повторно. Например, в первом базовом замере component.hpp встретился 4 раза и дал 3,02 с по отчёту анализатора. Времена вложенных заголовков при этом нельзя просто складывать.
4) Линковка тоже занимает много времени: её медиана составила 13,03 с при медиане всей сборки 25,38 с. Получается, примерно половину времени приходится ждать именно её.

Для проверки добавил PCH с component.hpp для пяти файлов userver_study_objs. Идея была в том, чтобы компилятор использовал уже подготовленный заголовок и меньше разбирал одно и то же. Время подготовки PCH тоже учитывал, код самого сервиса не менял. Суммарное время разбора уменьшилось с 25,88 до 21,06 с, примерно на 18,6%. Но полная сборка изменилась с 25,38 до 24,71 с по медиане, то есть всего на 2,6%. Исходные замеры: 24,00; 26,35; 25,38 с. С PCH: 24,71; 24,66; 24,90 с. По этим трём повторам пока не стал бы говорить, что способ устойчиво ускоряет сборку. Возможно, для этого сервиса выигрыш небольшой, а линковка всё равно занимает много времени.

По ходу сборка сначала падала при линковке. Причина оказалась в сжатии отладочной информации: Clang использовал zstd, который не поддерживает GNU ld 2.38 из образа. Проверил это на отдельном маленьком примере. В обоих вариантах выставил USERVER_DEBUG_INFO_COMPRESSION=z, после чего они собрались и прошли запуск с --help. Это общая настройка для двух вариантов, её не учитываю как результат PCH.

Дальше хотелось бы повторить замеры на Linux без эмуляции и посмотреть, что будет при пересборке после изменения одного общего заголовка. Пока результаты относятся к этому шаблонному сервису и сборке с включёнными трейсами на моём Mac. Работу с базами данных отдельно не проверял, запуск с --help проверяет только старт программы и вывод справки. Скрипты, логи и исходные замеры приложил архивом. После распаковки запуск через bash run.sh, результаты лежат в results/submitted, само изменение показано в optimization.patch.

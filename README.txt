Куда уходит время сборки userver-сервиса
Вячеслав Савельев, БПИ264

Отчёт: report.txt.

Запуск после распаковки архива:

    bash run.sh

Нужен работающий Docker с доступом в интернет. Скрипт использует именно образ из задания, запускает его с 4 ядрами, cpuset 0-3, лимитом памяти 8g и memory-swap 8g. Внутри контейнера устанавливается закреплённая версия Clang 18. Исходники Clang Build Analyzer уже лежат в vendor, их контрольная сумма проверяется перед сборкой. На компьютере не нужны Python, CMake или установленный userver.

По умолчанию выполняются по одному прогревочному запуску каждого варианта и по три измеряемые сборки. Для короткой проверки работоспособности можно выполнить RUNS=1 bash run.sh. Результат такой проверки не заменяет серию из нескольких повторов.

Результаты нового запуска появятся в results/<дата-время>. Предыдущие измерения не перезаписываются. В results/LATEST записывается имя последнего успешного запуска. Исходные результаты, на которых основан отчёт, находятся в results/submitted.

Что измеряется

Сервис создаётся внутри образа командой userver-create-service --grpc --mongo --postgresql userver_study. Собирается Release цель userver_study с помощью Ninja и четырёх параллельных процессов. Библиотеки самого userver берутся из образа. Юнит-тесты и бенчмарки не входят в измеряемую цель.

Каждая сборка начинается в новом каталоге. Кэши ccache и sccache отключены, CMake compiler launcher пустой. Один запуск каждого варианта нужен для прогрева файловой системы и не входит в итоговую статистику. Затем порядок чередуется: baseline/optimized, optimized/baseline, baseline/optimized. Во время измерений код, compiler flags, число процессов и ресурсы одинаковые; различается только настройка PCH.

Время сборки измеряется вокруг cmake --build. Создание сервиса, установка компилятора, конфигурация CMake, сборка анализатора и обработка трейсов в него не входят. Дополнительно сохраняется .ninja_log: по нему отдельно видно время до готовности объектных файлов и длительность линковки. Это не замер CPU time.

Трейсы записываются с -ftime-trace -ftime-trace-granularity=500. Трейсы проверок компилятора, которые CMake создаёт при конфигурации, удаляются до начала измерения. Clang Build Analyzer вызывается через --start, --stop и --analyze. Его исходный вывод сохранён без редактирования.

Проверяемое изменение

В optimized добавлена одна настройка:

    target_precompile_headers(${PROJECT_NAME}_objs PRIVATE <userver/components/component.hpp>)

Она включает предкомпилированный заголовок для пяти исходных файлов объекта userver_study_objs. Подготовка самого PCH каждый раз входит в чистую сборку. Генерируемые gRPC файлы и main.cpp используют прежние настройки. Точный diff лежит в optimization.patch. Другие файлы сервиса не меняются.

Исправление окружения, общее для обоих вариантов

Clang 18 поддерживает -gz=zstd, а GNU ld 2.38 из образа не умеет обрабатывать соответствующие отладочные секции. Автоматическая настройка userver выбирает несовместимое сочетание. Поэтому в обоих вариантах явно задано -DUSERVER_DEBUG_INFO_COMPRESSION=z. Это исправление сборки, оно не считается проверяемой оптимизацией. Первоначальная ошибка и отдельный пример для её воспроизведения сохранены в diagnostics и compression-probe.txt.

Как устроены результаты

summary.json: сводка и медианы; measurements.json: все запуски, включая прогревочные; environment.json: компилятор, CMake, Linux, доступные ресурсы и методика; packages.txt: установленные пакеты; sources: точные исходники двух вариантов; optimization.patch: единственное различие вариантов. В папке каждого запуска находятся analysis.txt, capture.bin, исходные JSON трейсы, compile_commands.json, CMakeCache.txt, .ninja_log, build.log и metrics.json. service-help.txt подтверждает проверку запуска собранного бинарного файла с --help. Это не функциональное тестирование сервиса с базами данных.

Ограничения

Основная серия снята на Apple M5 с 16 ГБ памяти через Docker Desktop и эмуляцию linux/amd64. Контейнер получил ограничения из задания; память Linux VM может быть меньше самого лимита контейнера, точные значения сохранены. Абсолютные времена не следует переносить на обычную x86-64 Linux машину. Три повтора показывают разброс этой серии, но не дают основания обещать такой же эффект на других проектах. Суммарные длительности компиляторов не равны времени ожидания сборки при параллельном запуске. Время вложенных заголовков и шаблонов нельзя складывать как независимые затраты.

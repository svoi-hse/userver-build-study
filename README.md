# Куда уходит время сборки userver-сервиса

Вячеслав Савельев, БПИ264. Тестовое задание по теме «Ускорение сборки C++-сервисов на открытом фреймворке userver».

Посмотрел, на что уходит время сборки шаблонного сервиса, и проверил одну идею: использовать предкомпилированный заголовок `component.hpp`. Разбор кода стал занимать меньше времени, но по трём повторам устойчивого ускорения всей сборки не видно.

## Запуск

Нужен работающий Docker с доступом в интернет. После скачивания и распаковки исходников репозитория достаточно выполнить в его папке:

```bash
bash run.sh
```

Скрипт сам подготовит инструменты внутри контейнера, создаст сервис и выполнит замеры. На компьютере не нужно отдельно устанавливать Python, CMake или userver. Используется образ из задания с закреплённым digest, четырьмя ядрами и лимитом памяти 8 ГБ.

Для каждого варианта выполняется один прогревочный запуск, затем три измеряемые сборки. Порядок вариантов чередуется, каталоги сборки каждый раз новые, кэши компиляции отключены. Измеряется `cmake --build`, включая создание PCH, генерацию кода и линковку. Установка инструментов и настройка CMake в это время не входят.

Результаты появятся в `results/<дата-время>`. Имя последнего успешного запуска записывается в `results/LATEST`. Для короткой проверки можно выполнить `RUNS=1 bash run.sh`, но одного повтора недостаточно для сравнения времени сборки.

## Что получилось

| Показатель, медиана трёх запусков | Обычная сборка | С PCH |
| --- | ---: | ---: |
| Время всей сборки | 25,38 с | 24,71 с |
| Суммарное время frontend по трейсам компилятора | 25,88 с | 21,06 с |

Суммарное время frontend уменьшилось примерно на 18,6%, а время всей сборки в этой серии на 2,6%. Файлы компилируются параллельно, поэтому эти показатели нельзя приравнивать. Медиана линковки обычного варианта составила 13,03 с: она занимает примерно половину времени всей сборки и этим изменением не ускоряется напрямую.

Замеры сделаны на Apple M5 с 16 ГБ памяти через Docker Desktop и эмуляцию `linux/amd64`. Абсолютные времена относятся к этому окружению. Следующий шаг, который хотелось бы проверить, это повторение эксперимента на Linux без эмуляции и пересборка после изменения общего заголовка.

## Как устроены скрипты

`run.sh` запускает Docker с нужным образом и ограничениями. `scripts/in-container.sh` устанавливает закреплённый Clang и собирает анализатор из архива в `vendor`. `scripts/experiment.py` создаёт сервис, проводит сравнение и сохраняет результаты. `scripts/compression_probe.py` отдельно проверяет причину первоначальной ошибки линковки.

В обоих вариантах задано `USERVER_DEBUG_INFO_COMPRESSION=z`: это исправляет несовместимость сжатия zstd с GNU ld 2.38 из образа. Эта настройка общая для двух вариантов и не считается проверяемой оптимизацией. Готовые программы проверены запуском с `--help`; работа сервиса с базами данных отдельно не тестировалась.

Использованы [userver](https://github.com/userver-framework/userver) и [Clang Build Analyzer](https://github.com/aras-p/ClangBuildAnalyzer). Исходники анализатора, его лицензия и лицензии зависимостей находятся внутри `vendor/ClangBuildAnalyzer.tar.gz`. Точная версия и SHA256 архива указаны в `versions.json`.
